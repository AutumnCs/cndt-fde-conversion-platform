# CNDT FDE 招商中台 MVP 技术设计（暂定）

状态：总体设计已确认，待业务复核  
日期：2026-09-28

## 1. 目标与边界

本项目建设面向内部团队的海外消费者获客与咨询转化中台，围绕 CNDT 硬件产品建立“宣发获客、Telegram 接待、人工成交协作、运营复盘”的可审计闭环。

硬件钱包、KYC 终端、商城支付、库存物流、设备激活、链上/代币/DeFi 服务均不属于本项目开发范围。它们可在未来通过受控接口回传必要的成交或服务状态。

## 2. 推荐路线

采用模块化单体核心加可替换连接器：核心业务状态由 CNDT 中台自主管理；渠道、模型、通知、分析与未来外部系统通过边界清晰的连接器接入。MVP 不采用微服务拆分，也不以第三方客服或自动化平台作为客户、线索、审批或审计的事实源。

## 3. 总体技术脉络

```text
视频传媒矩阵 → 可追溯入口 → Telegram 接待 → 线索分级 → 经理确认
       ↑                                                    ↓
内容合规、AI 宣发官、渠道数据                         专员跟进、结果回填
       └─────────────────── 运营指标与审计 ───────────────────┘

Telegram 与未来渠道连接器
          ↓
渠道接入层 → CNDT 招商核心（CRM、会话、Agent、知识库、审批）
          ↓
运营基础（权限、审计、队列、通知、指标、配置版本）
          ↓
模型、对象存储、分析工具及后续外部系统接口
```

## 4. 模块与技术安排

| 模块 | 职责 | 暂定安排 |
| --- | --- | --- |
| 视频传媒矩阵 | 视频策略、素材与制作、内容计划、活动、渠道账号目录、发布审批、入口归因、内容效果复盘 | 自研 Campaign、ContentAsset、VideoVariant、ContentVersion、ChannelAccount、Publication、AttributionLink 与 AttributionEvent 模型；素材放对象存储，状态、版权/授权和审核元数据存 PostgreSQL。 |
| 渠道接入 | Telegram 消息接入，未来渠道的发布、入站消息和指标同步 | 每个渠道实现独立 Connector；统一能力声明（授权、发布、入站消息、指标）。一期只正式启用 Telegram，其他渠道仅建模与预留接口。 |
| AI 宣发官 | 辅助生成中英文内容草稿、渠道格式建议、CTA 和活动文案 | 不直接对外发布；读取已审核产品资料和渠道模板，生成草稿后由内容合规负责人审批。提示词、知识范围、触发规则和版本可追溯。 |
| AI 客服官 | Telegram 中英文答疑、初步意向判断、会话摘要、人工转接 | 风险策略前后双检，限定检索已发布且外部可见的知识库。AI 仅提出分级建议，不直接承诺、分配或成交。 |
| 客户与线索 CRM | 客户身份、来源、兴趣、意向、A/B/C、分配、任务和结果 | PostgreSQL 为业务事实源；以 Telegram 用户 ID 建立初始身份，客户同意后才合并跨渠道联系方式。 |
| 知识库与合规 | 中英文资料、FAQ、话术、受限话题、审批、发布和回滚 | 先用 PostgreSQL 全文检索加 pgvector；每个知识条目带语言、受众、审批状态和版本。规则优先于语义检测。 |
| 人工成交工作台 | 经理确认、专员承接、内部备注、预约及结果回填 | Web 管理端；分配、改级、接管、知识/提示词发布均记录操作者、时间、前后值和版本。 |
| 工作流与通知 | 待确认、超时提醒、日报、未来系统同步 | 业务任务表加 Redis 队列；可选 n8n 仅用于非关键外围集成，不能保存关键业务状态。 |
| 看板与观测 | 来源效果、咨询、分级、响应、人工转化、AI 质量 | 业务指标由业务事件计算；网站流量可接 PostHog。AI 调用可使用 Langfuse 做脱敏追踪、评测和提示词实验。 |

## 5. 视频传媒矩阵设计

### 5.1 它解决的问题

视频传媒矩阵是获客发动机：它把合规的原创/授权素材变成多语言、适配渠道的视频发布包和可追溯入口，再把效果送回 CRM。它不负责批量控号、虚假互动、未获同意的触达、个人数据爬取、内容搬运或绕过平台规则。

### 5.2 内容到线索的链路

```text
已授权产品资料/原创素材
→ AI 宣发官生成选题、脚本、字幕/标题与封面建议
→ 视频制作、转码与渠道格式导出
→ 内容合规负责人审批
→ 内容版本与活动绑定
→ 人工发布或官方 API 发布
→ 带渠道/内容/活动标识的落地页或 Telegram 深链接
→ 用户主动咨询
→ CRM 创建来源明确的客户和线索
→ 咨询、意向、预约、成交结果回写活动看板
```

### 5.3 技术责任划分

| 子模块 | 主要数据 | 规则 |
| --- | --- | --- |
| 视频资产库 | 原始素材、脚本、成片、封面、字幕、配音、授权/版权、语言、产品版本、审核状态 | 没有授权、来源或有效期的素材不可进入发布流程；转码、字幕和格式导出经异步任务执行。 |
| 视频内容工作流 | 选题、草稿、审核意见、版本、渠道模板、CTA、不同画幅/时长成片 | AI 只能创建草稿和发布包；合规负责人可批准、退回或撤回。 |
| 活动与渠道 | 活动目标、目标市场、账号、预算字段、落地页 | 渠道账号必须标明归属和授权状态；未获授权不能连接。 |
| 归因链接 | 链接、UTM、渠道、内容、活动、目标入口 | 一条对外内容对应一个可追溯入口；链接服务只记录必要事件。 |
| 发布编排 | 发布计划、人工发布清单、官方 API 发布任务、结果 | 只有平台正式支持且已获授权时，才允许 API 发布；失败可重试并记录原因。 |
| 效果回流 | 曝光/点击等聚合指标、咨询、A/B/C、预约、成交 | 北极星指标是有效咨询和人工确认的高意向/成交，不以刷量式互动优化。 |

### 5.4 分期

| 阶段 | 宣发矩阵交付 | 渠道状态 |
| --- | --- | --- |
| Telegram MVP | 视频资产库、脚本/字幕/封面发布包、合规审批、AI 宣发草稿、活动、专属入口、来源归因与基础看板 | 对外视频由人工在已授权账号发布；Telegram 是唯一正式接待渠道。 |
| 下一阶段 | 一个优先外部内容渠道的官方 API 连接器、发布状态与聚合指标回流 | 以平台允许的权限、目标市场与账号类型核验结果为准。 |
| 后续 | 多渠道连接器、广告/KOL 合作数据、跨渠道归因和实验 | 逐渠道独立立项、权限评审与验收。 |

## 6. 关键实现选择

- 后端：TypeScript 模块化服务，API 与后台任务分离；初期采用模块化单体，避免微服务运维成本。
- 数据：PostgreSQL 保存业务事实、审批和审计；Redis 承担限流、缓存与异步任务；对象存储保存审核通过的素材和文档。
- 管理端：React/Next.js，按角色显示内容审批、经理队列和专员工作台。
- Telegram：官方 Bot API Webhook，接入库候选 Telegraf；原始更新先持久化并按事件 ID 去重。
- 知识检索：PostgreSQL 全文检索 + pgvector；当资料规模、并发或隔离要求证明需要时，再评估 Qdrant。
- AI：模型供应商适配层隔离具体模型；所有调用带配置版本、检索来源、风险命中和人工评分入口。
- 可观测性：应用指标与审计自管；Langfuse 仅承担经脱敏审查后的 AI 追踪、评测与提示词实验。
- 安全：最小权限 RBAC、凭证密钥管理、敏感资料访问审计、备份与恢复演练；不在 Git 或聊天中保存生产凭证。

## 7. MVP 验收主线

1. 合规负责人发布一份中英文产品资料和一条活动内容。
2. 运营人员为该内容生成唯一 Telegram 深链接，并人工发布到已授权外部账号。
3. 用户经链接主动发起 Telegram 对话，系统保留准确来源。
4. AI 客服官在受控知识范围内答疑、拦截受限话题并建议 A/B/C 分级。
5. 经理确认高意向线索并分配专员；专员回填跟进和结果。
6. 看板可由活动内容追溯到咨询、分级、人工接管和成交结果；全过程可审计。

## 8. 暂不纳入

- 硬件、商城、支付、库存、物流、设备激活、链上和金融业务系统。
- 批量控号、刷量、骚扰式群发、个人信息爬取、竞争对手截流、内容搬运、规避平台规则。
- 未经逐渠道 API 权限与合规审查的自动化发布、KOL 或广告平台集成。
