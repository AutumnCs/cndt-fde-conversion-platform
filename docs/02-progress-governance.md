# 项目进度与长期维护治理

## 进度控制方式

项目以可验收里程碑推进，不以“完成多少页面”判断进度。

| 阶段 | 目标 | 完成门槛 |
| --- | --- | --- |
| 0. 发现与设计 | 冻结 MVP 范围、角色、流程、风险边界，并将原始 FDE 方案的差异写入决策记录。 | 设计文档获业务方确认。 |
| 1. Foundation 基础骨架 | 身份、权限、审计、数据模型、知识库隔离、风险策略和测试环境可用。 | 可创建内部账号、记录审计事件，且内部知识不进入对外知识库。 |
| 2. Telegram 链路 | 群聊/私聊消息稳定进入系统。 | 测试 Bot 在目标场景收发与留痕通过。 |
| 3. AI 与线索 | 中英文受控答复、分级、经理确认和人工接管可用。 | 以脱敏测试集通过关键对话、风险拦截、权限和重复线索验收。 |
| 4. 内部试点 | 团队真实使用、收集指标与问题。 | 关键指标和异常清单完成复盘。 |
| 5. 规模化 | 扩充渠道、经销商后台或其他已批准能力。 | 每项扩展独立评审、设计和验收。 |

## 长期维护机制

- 每项关键选择写入 `docs/decisions/`，避免口头决策丢失。
- 每周更新一次本文件和 `OPEN_QUESTIONS.md`：已完成、风险、下周目标、待决事项。
- 每次发布包含：变更说明、数据库迁移说明、回滚方案、测试结果和负责人。
- 内容合规负责人审批后才可发布知识库、提示词和对外话术；所有版本可回滚。
- 每月复核：渠道 API 权限、Bot Token 轮换、成员权限、日志保留、数据脱敏和成本。
- 先使用测试 Bot、测试群和脱敏测试数据；正式凭证只存放在受控密钥管理系统。
- 上线门槛参考正式材料的首轮全量测试：业务主线、知识库隔离、风险拦截、多轮会话、语言、权限、API 预埋和异常场景均须有 PASS/FAIL 记录；失败项修复并回归通过后才可进入试点。

## Agent 与 Skill 使用策略

- 当前设计阶段：由主代理维持单一事实源，避免多个 Agent 对需求做出相互矛盾的结论。
- 实施阶段：仅将可独立验收的工作交给 Agent，例如 Telegram 接入、CRM 界面、测试、开源安全审查。
- 每个 Agent 的产出必须通过代码审查、自动测试和主分支验收，不能直接接触生产凭证。
- 使用技能的顺序：需求澄清与设计 → 实施计划 → 测试驱动开发 → 安全/性能审查 → 发布前验证。
